built, composed and routed across platforms, and what a library version would have to change. sini/nix-config is the
audit maintainer's own configuration and the rubric's reference anchor. It is the upper reference for I, O and X, and
it has real deductions elsewhere (§9), so the study also lists its defects.

## 1. Repository layout and discovery

- `flake.nix:7` is the whole flake:
  `outputs = inputs: inputs.flake-parts.lib.mkFlake { inherit inputs; } (inputs.import-tree ./modules);`.
  `flake.nix` is generated by flake-file (`flake.nix:1-2`), and inputs are declared in modules
  (see §5).
- import-tree loads every `.nix` file under `modules/`. Files and directories whose
  names start with `_` are skipped, and the code relies on this for helper files
  (`modules/den/schema/_settings-type.nix:8-9`, `modules/flake-parts/_lix.nix:9`,
  `A/secrets/_generators-module.nix:6`). Helpers are pulled in with an explicit `import`
  (`A/core/nix/nix.nix:119`, `modules/den/batteries/agenix.nix:15`).
- den is mounted once, at `modules/den/flake-parts.nix:3` (`imports = [ inputs.den.flakeModule ];`).
- What lives where under `modules/den/`:

| dir / file | holds |
|---|---|
| `aspects/<category>/…` | the aspect library. Categories: applications, core, desktop, devshell, disk, domain, hardware, kubernetes, macos, roles, secrets, services, virtualization |
| `hosts/<name>.nix` | one file per host, setting `den.hosts.<system>.<name>` and `den.aspects.<name>` |
| `users/<name>.nix` | `den.aspects.<user>` and `den.users.registry.<user>` |
| `environments/{dev,prod}.nix`, `clusters/`, `groups/`, `access.nix` | topology entities and access grants |
| `policies/*.nix` | how the scope tree is wired (flake → fleet → env → host → user), plus pipe collection |
| `quirks/*.nix` | declarations of the data channels (`den.quirks.<name>.description`) |
| `schema/*.nix` | entity option schemas (host, user, cluster, environment, …) |
| `batteries/*.nix` | fleet batteries (agenix, colmena, nixidy, nix-on-droid, panix) |
| `classes/*.nix` | extra classes (homeLinux/homeDarwin/homeAarch64, devshell, panix) |
| `defaults.nix` | `den.default`, default host and user includes, `inputs'`/`self'` overrides |

- **The file path is the identity path, and the file says so itself.** Each file assigns its
  full identity, for example `A/roles/workstation.nix:3` sets `den.aspects.roles.workstation`.
  No namespace function derives the name from the path: `den.namespace`, `__findFile` and
  `<den/…>` have 0 hits under `modules/`. For 430 of the 447 aspect files, the identity path is
  the file path or its parent. The 17 exceptions are mostly `*-check.nix` flake checks, plus
  `A/virtualization/guests.nix`.
- When a directory is itself an aspect, its file is named after the directory:
  `A/core/network/tailscale/tailscale.nix:5` sets `den.aspects.core.network.tailscale`.
  `default.nix` is not special. `A/roles/default.nix:3` defines an aspect actually named
  `roles.default`.
- **One aspect can be split across files.** Each file contributes one key to the same aspect,
  and den merges them:
  - `tailscale.nix:5` contributes `nixos`
  - `tailscale/secrets.nix:4` contributes `.age-secrets`
  - `tailscale/darwin.nix:5` contributes `.darwin`
  - `tailscale/exit-node.nix:4` contributes `.exit-node`, a child aspect

  `A/core/network/syncthing/member.nix:13,15` assigns two keys at the leaf the same way.
- Tests live next to the aspect they test. `A/services/scanning/epson-scan-check.nix:13-23`
  is a flake-parts `perSystem` check in the aspects tree, because import-tree loads any
  module wherever it sits.

## 2. Aspect anatomy

### Canonical aspect, quoted in full: `A/services/security/acme.nix`

This one file shows typed settings, a parametric class key that reads host, environment and
quirk data, a secret emitted through a quirk, and persistence emitted through a quirk.

```nix
{ lib, ... }:
{
  den.aspects.services.security.acme = {
    settings = {
      fqdnCert = lib.mkOption {
        type = lib.types.bool;
        default = false;
        description = "Order a certificate for the host's FQDN and its wildcard";
      };
    };

    nixos =
      {
        config,
        environment,
        host,
        certificate-domains,
        ...
      }:
      let
        # Extract top-level domain from the host's FQDN
        fqdnParts = lib.splitString "." config.networking.fqdn;
        topDomain = lib.concatStringsSep "." (lib.reverseList (lib.take 2 (lib.reverseList fqdnParts)));
      in
      {
        security.acme = {
          acceptTerms = true;
          defaults = {
            email = (environment.email or { }).adminEmail or "admin@${topDomain}";
            inherit ((environment.acme or { })) dnsProvider;
            inherit ((environment.acme or { })) dnsResolver;
            dnsPropagationCheck = true;
            credentialFiles =
              let
                domainConfig = lib.findFirst (d: d.domain == topDomain) null certificate-domains;
                issuerName = if domainConfig != null then domainConfig.issuer else null;
              in
              lib.optionalAttrs (issuerName != null) {
                CLOUDFLARE_DNS_API_TOKEN_FILE = config.age.secrets."${issuerName}-cloudflare-api-key".path;
              };
          };

          certs = lib.mkIf host.settings.services.security.acme.fqdnCert {
            ${config.networking.fqdn}.extraDomainNames = [ "*.${config.networking.fqdn}" ];
          };
        };
      };

    age-secrets =
      { environment, host, ... }:
      let
        issuers = environment.certificates.issuers or { };
      in
      {
        # Plain disjoint merge (one secret per issuer), not mkMerge: the secrets
        # collector deduplicates broadcast emissions by name with a shallow
        # merge, so emitters must return a plain attrset.
        age.secrets = lib.mergeAttrsList (
          lib.mapAttrsToList (
            issuerName: issuer:
            lib.optionalAttrs (issuer.ageKeyFile or null != null) {
              "${issuerName}-cloudflare-api-key" = {
                rekeyFile = issuer.ageKeyFile;
              };
            }
          ) issuers
        );
      };

    persist = {
      directories = [
        {
          directory = "/var/lib/acme";
          user = "acme";
          group = "acme";
          mode = "0755";
        }
      ];
    };
  };
}
```

### The recurring structure

- **The module header.** It destructures only what the file uses at flake level: `{ lib, ... }`,
  `{ den, ... }` (for `includes`), `{ inputs, ... }`, `{ self, ... }`. When a file needs none
  of these it is a bare attrset (`A/hardware/bluetooth.nix:1`).
- **Keys inside an aspect, by how often they appear.** Counts are the number of lines indented
  at aspect level under `A/`, so they are approximate:
  - class keys: `nixos` 158, `homeManager` 140, `k8s-manifests` 77, `darwin` 16,
    `homeLinux` 15, `homeDarwin` 8, `os` 8
  - structural keys: `includes` 60, `settings` 33
  - quirk keys: `age-secrets` 63, `service-domains` 48, `served-domains` 45, `persist` 32,
    `agent-extensions` 27, `firewall` 15, `persistHome` 12, `homeManagerModules` 12,
    `nixpkgs-overlays` 11
- **A class key is either a plain attrset or a function of the den context.** In the function
  form, den passes context alongside the normal module arguments (`pkgs`, `lib`, `config`):
  - entity arguments: `host`, `user`, `environment`
  - every quirk, by name, as a list of emissions: `certificate-domains`, `nix-builders`,
    `nixpkgs-overlays`, `resolved-users`
  - the per-system inputs: `inputs'`, `self'`

  Examples: `acme.nix:12-19`, `A/core/nix/remote-build-client.nix:6-12`,
  `A/core/nix/nixpkgs.nix:28-29`.
- **The function is at the class key, not at the aspect.** Aspects are attrsets whose class
  keys are functions. The templates' `den.aspects.cooper = { user, ... }: { … }` form (see §7)
  does not appear in a quick grep of `A/`. The grep looked for `den.aspects.X =` followed by an
  argument pattern. It found only class or quirk leaves, such as `tailscale/secrets.nix:4-5`.
  That grep was not exhaustive.
- **`includes`** is nearly always `with den.aspects; [ … ]` with comment group headers
  (`A/roles/workstation.nix:4-41`). A battery can be applied to arguments inside `includes`:
  `(den.batteries.unfree [ "corefonts" "vista-fonts" ])` (`A/desktop/style/fonts/regular.nix:5-8`).
  An aspect includes the aspects it depends on: `roles.nix-builder` includes
  `services.nix.remote-build-server` (`A/roles/nix-builder.nix:4-6`).
- **`provides` is unused.** Its 6 hits are all in comments. Aspects never use `provides.*`,
  `_.`, `mutual-provider` or `forward`.
- **The difference between `settings` and options.**
  - `settings` is a reserved, non-dispatched key (`modules/den/defaults.nix:129`,
    `den.reservedKeys = [ "settings" ]`). Its value is an attrset of `lib.mkOption`s,
    which is where the defaults live (`A/core/nix/nix.nix:8-32`).
  - `modules/den/schema/_settings-type.nix:41-89` walks `den.aspects`. It skips structural,
    class and quirk keys (`:13-16`), and mirrors every aspect that declares `settings` into a
    typed submodule. That submodule is mounted as `host.settings` (`schema/host.nix:315-324`).
    `schema/cluster.nix` mounts the same type, per the comment at `_settings-type.nix:1-7`.
  - A host sets values by identity path (`hosts/cortex.nix:33-56`, for example
    `core.nix = { maxJobs = 4; cores = 8; }`).
  - An aspect reads them back by its own full path (`A/core/nix/nix.nix:49-50`,
    `host.settings.core.nix.maxJobs`).
  - The code names this "the bgp pattern: the aspect declares, the host file sets"
    (`A/roles/nix-builder.nix:8-9`, `A/core/nix/nix.nix:4`). It is written up for re-use in
    `docs/host-aspect-settings.md`.
  - Aspects do not declare NixOS `options` for per-host knobs. A host-level override that
    falls outside settings goes in the host's own `nixos` block (`hosts/blade.nix:53-76`).
- **User settings are freeform and untyped.** They are written as
  `den.users.registry.<u>.settings.<feature>` (`modules/den/users/sini.nix:16-17`) and read with
  an `or` default (`A/applications/dev/git/git.nix:56`,
  `user.settings.git.signing.method or "none"`). The schema is
  "freeform nested namespace" (`modules/den/schema/user.nix:137-140`).
- **Quirk keys are how an aspect emits data.** An aspect puts data under a sibling key named
  after a quirk, either a value or a function of context. A collector aspect receives every
  emission as a list and folds it:
  - `persist` is folded by `A/core/impermanence/persist-collector.nix:3-19`
  - `age-secrets` by `A/core/secrets/collector.nix:17-31`
  - `firewall` by `A/core/network/firewall-collector.nix:1-5`, which is just `lib.mkMerge firewall`
  - `homebrew-cask` by `A/macos/homebrew.nix:12-22`

  Each quirk is declared in a one-line file, for example `modules/den/quirks/firewall.nix:2`.

## 3. Composition: how hosts and users get their aspects

- **Applied everywhere** (`modules/den/defaults.nix`):
  - `den.default.includes`, lines 201-208: den's `define-user`, `hostname`, `inputs'` and
    `self'` batteries.
  - `den.schema.host.includes`, lines 150-153: the firewall and secrets collectors.
  - `den.schema.user.includes`, lines 156-196:
    - the resolved-user emitter
    - `user-aspect-auto-include` (166-175), which includes `den.aspects.<host>.<user>`
      when that aspect exists
    - `primary-user-for-owner` (186-195), which applies den's `primary-user` battery only
      when `user.name == host.system-owner`. The stated reason is that wheel must not follow
      from simply being able to log in (177-181).
- **A host composes roles.** `den.aspects.<host>.includes` lists `roles.*` and then
  `hardware.*`, `disk.*` and similar (`hosts/cortex.nix:59-96`).
  - `roles.default` is the NixOS baseline: nix, boot, users, impermanence, ssh, tailscale and
    agenix (`A/roles/default.nix:3-41`).
  - `roles.workstation` and the other roles are flat include lists (`A/roles/workstation.nix`).
  - Raw tweaks for one host go in the host aspect's `nixos`, `darwin` or `home-manager`
    blocks (`hosts/cortex.nix:98-220`, `hosts/patch.nix:28-36`).
- **Per-user variation on one host.** The host aspect gets a nested attribute named after the
  user, `den.aspects.cortex.sini.includes = [ … ]` (`hosts/cortex.nix:222-232`), and
  `user-aspect-auto-include` picks it up.
- **Users get onto hosts by policy, not by listing.** NixOS hosts do not set
  `den.hosts.<s>.<h>.users`. The path is:
  1. `den.users.registry.<u>` holds the user's `groups`, `system.uid` and `identity`
     (`users/sini.nix:7-55`). The registry type extends `den.schema.user`
     (`policies/users.nix:41-75`).
  2. `access.nix:6-17` grants groups to environments.
  3. `policies/fleet.nix:50-89` (`env-to-hosts`) works out `accessGroups` per host as
     (environment grant ∪ host grant ∪ host `system-access-groups`), intersected with the
     host's access gate.
  4. `policies/users.nix:106-114` (`env-users`) resolves every registry user whose groups
     intersect `accessGroups`.
  5. den's built-in `host-to-users` is excluded (`policies/fleet.nix:103`), and `env-users` is
     wired in through `policies/hosts.nix:8-10`.

  Users with `classes = [ ]` are identity-only (SSO, no Unix account;
  `users/identity-only.nix:3-7`). The non-NixOS hosts list users explicitly
  (`hosts/patch.nix:10`, `hosts/slab.nix:10`).
- **What a user's own aspect pulls in.**
  - Most users include `roles.default` (`users/dvicory.nix:3-5`), which gives them that role's
    `homeManager` half.
  - **Inference:** the `nixos` half of a role included at user scope does not produce a second
    copy. I did not verify this.
  - sini instead includes den's `host-aspects` battery (`users/sini.nix:3-5`). That battery
    projects the `homeManager` content of the whole host aspect tree onto the user
    (den `modules/aspects/batteries/host-aspects.nix:3-14`).
  - The result: a host's roles configure the owner's home. Other users get only `roles.default`
    plus their per-host includes.
- **Topology as scope.** The policies build the chain flake → fleet → environment → host →
  user (`policies/fleet.nix:20-94`). `environment` and `secretsConfig` are inherited down the
  scope, which is why `acme.nix` can destructure `environment`. Environments carry fleet data
  such as domain, networks, issuers and service delegation (`environments/dev.nix:4-40`).
- **Policies that belong to an aspect sit in the aspect's file.** An aspect that needs
  cross-host collection declares `den.policies.<name>` and adds it to
  `den.schema.host.includes` in the same file. Examples: `A/applications/dev/ai/mcp/xmsg.nix:62,70`,
  `A/services/ai/ninfer.nix:53,69`, and `quirks/nixpkgs-overlays.nix:20-26` for a quirk.
  The fleet-wide pipes sit together in `policies/pipes.nix`.
- **Cross-host data uses quirks plus pipes.** A producer emits per-host data and every peer's
  consumer reads the collected list:
  - Producer: `A/roles/nix-builder.nix:40-48` emits `nix-builders = { host, ... }: { hostname; ip; system; … }`.
  - Collector: `policies/pipes.nix:67-74`, `pipe.from "nix-builders" [ (pipe.collectAll …) ]`.
  - Consumer: `A/core/nix/remote-build-client.nix:9,14` destructures `nix-builders` and
    filters out the host itself.
  - `pipe.collect` stays within the environment and `pipe.collectAll` spans the whole fleet.
    The comments at `policies/pipes.nix:70,100` make this explicit.
- **Checks on aspect membership.** `host.hasAspect den.aspects.roles.workstation` changes
  behaviour depending on what else is composed onto the host (20 uses, for example
  `A/applications/dev/security/bitwarden.nix:63` and `batteries/agenix.nix:31`).

## 4. Platform handling

- **Classes.** `nixos`, `darwin`, `os` (shared by nixos and darwin, from den's os-class, per the
  comment at `defaults.nix:199-200`), `homeManager`, and the platform-routed home classes. Hosts
  are NixOS (`den.hosts.x86_64-linux.*`), darwin (`hosts/patch.nix:3-5`,
  `system = "aarch64-darwin"`) or nix-on-droid (`hosts/slab.nix:3-5`, `class = "droid"`,
  aarch64-linux). The config has no standalone `den.homes` (0 hits).
- **One aspect can carry several class arms.** `A/core/nix/nix.nix` has `os` (34), `darwin`
  (90) and `nixos` (106). `A/core/nix/nixpkgs.nix` has `os` (28) and `homeManager` (42).
- **Platform-routed home classes.** `modules/den/classes/home-platform.nix:3-5` declares
  `homeLinux`, `homeDarwin` and `homeAarch64`. Policies at user scope (`:7-56`) route each one
  into `homeManager` only when `host.system` matches. For example, chromium puts its Linux-only
  config in `homeLinux` and its macOS install in `homebrew-cask`
  (`A/applications/browsers/chromium.nix:1-5,47-50`).
- **A quirk with no consumer does nothing.** `homebrew-cask` is consumed only by
  `macos.homebrew`, which only `roles.darwin-workstation` includes
  (`A/roles/darwin-workstation.nix:14`). A Linux host can include chromium and its cask
  emission is never collected. `persist` works the same way: it takes effect only where
  `core.impermanence` includes the collector (`A/core/impermanence/impermanence.nix:10`).
- **Guards inside a class body**, when the aspect stays shared:
  - `pkgs.stdenv.hostPlatform.isLinux` (`A/applications/dev/ai/mcp/serena.nix:10`)
  - `pkgs.stdenv.isDarwin` (`A/applications/terminals/ghostty.nix:11`)
  - `host.class == "darwin"` (`A/applications/dev/security/ssh.nix:21`)
  - option-presence probes such as `config.microvm.host.enable or false` (`A/core/nix/nix.nix:117-118`)
  - only touching `age.secrets` when there is a secret, so that a host without agenix still
    evaluates (`A/core/secrets/collector.nix:22-27`)
- **A whole platform can opt out at the battery level.** `batteries/agenix.nix:36-38` keys on
  `${host.class}` and returns `{ }` for droid. `hosts/slab.nix:13-26` documents that a droid
  host skips `roles.default` and gets only the `homeManager` half of `roles.dev`.
- **Per-platform roles.** macOS is a separate role (`roles.darwin-workstation`) under its own
  `macos.*` category. It is not handled with conditionals inside `roles.workstation`
  (`A/roles/darwin-workstation.nix:1-4`).
- **Channels.** Each host picks a `channel` (`schema/host.nix:129-155,183-187`), and the
  channel selects nixpkgs, nix-darwin and home-manager together. A validator rejects unknown
  channel names (`:167-173`).

## 5. Inputs and secrets

- **Inputs are declared where they are used.** An aspect file writes
  `flake-file.inputs.<name> = { url = …; flake = false; }` above its `den.aspects` block
  (`A/applications/dev/ai/llm-agents.nix:5`, `A/applications/dev/ai/mcp/headroom.nix:11-14`).
  Then `nix run .#write-flake` regenerates `flake.nix` (`CLAUDE.md`).
  - 27 files under `modules/den` do this.
  - The 69 older or shared inputs stay in `modules/flake-parts/flake-file.nix:47+`
    (zen-browser, for example, at `:347`).
  - So the config uses both styles.
- **How inputs are used:**
  - `inputs'.<x>.packages.<p>` and `inputs'.<x>.homeModules.<m>` inside class functions
    (`llm-agents.nix:18`, `A/applications/browsers/zen-browser.nix:4-8`)
  - flake-level `inputs.<x>.nixosModules.<m>` in `imports` (22 sites, for example
    `A/core/nix/lix.nix:5,9`)
  - the fleet overrides den's `inputs'` and `self'` batteries (`defaults.nix:131-147`) so that
    they reach both the den context and `_module.args` for the host's and the users' classes
    (`defaults.nix:13-24`)
  - home-manager receives them through `extraSpecialArgs` (`A/core/users/home-manager/home-manager.nix:30-32`)
- **HM modules from inputs are a quirk.** `homeManagerModules = { inputs', ... }: [ … ]` is
  collected and imported by `core.users.home-manager-shared`
  (`quirks/home-manager.nix:2`, `A/core/users/home-manager/home-manager.nix:67,71`).
- **Secrets use agenix and agenix-rekey, through the `age-secrets` quirk.**
  - An aspect never writes `age.secrets` in its `nixos` block. It emits
    `age-secrets = { age.secrets.<n> = { rekeyFile | generator.script; owner; mode; }; }`
    and reads the decrypted path with `config.age.secrets.<n>.path` in its class body
    (`A/services/nix/remote-build-server.nix:26,60-69`, `remote-build-client.nix:26,42-47`).
    43 aspect files use `generator.script`.
  - The emitter rule is written at `A/core/secrets/collector.nix:13-16`: return a plain
    `{ age.secrets = …; }` and never `mkIf`/`mkMerge`. Express conditions with
    `optionalAttrs`/`mergeAttrsList` instead. `acme.nix` follows it.
  - `batteries/agenix.nix:23-74` wires the battery from the scope. It reads `secretsConfig`
    (master identities, `modules/den/secrets-config.nix`), `host.public_key` and
    `host.secretPath`.
  - The schema defaults are `.secrets/hosts/<name>` and `hosts/<name>/facter.json`
    (`schema/host.nix:334-338`).
  - A secret file that is optional is gated with `builtins.pathExists` (13 files, for example
    `A/core/network/tailscale/darwin.nix:14-18`).
- **What an aspect may assume about its context:**
  - `host` has `name`, `system`, `class`, `ipv4`, `secretPath`, `system-owner` and `settings`
  - `environment` is the host's environment entity (domain, networks, issuers, services)
  - `user` is a registry entry
  - every quirk named as an argument arrives as a list, possibly empty
  - `pkgs.local.*` is this flake's own packages, provided by the overlay at
    `A/core/nix/nixpkgs.nix:23-26` (used in 22 files)

## 6. Naming and conventions

- Identity paths are kebab-case and categorised (`hardware.gpu.nvidia-vfio`,
  `services.security.acme`). They are treated as stable API, because host `settings` and
  colmena tags (`@roles/workstation`) address them (`CLAUDE.md`).
- One aspect per file is the norm. Only 9 files define more than one top-level
  `den.aspects.*`. The opposite case, one aspect split over several files, is described in §1.
- Collectors, emitters and roles are named for what they do: `*-collector`, `resolved-user-emitter`
  and `roles.*`. A role contains only `includes`.
- Comments: 244 of 447 aspect files begin with a `#` header comment saying what the aspect
  is for and why. Inside the files, comments explain why a choice was made, often with a
  measurement:
  - `hosts/blade.nix:56-70` gives undervolt figures
  - `hosts/bitstream.nix:32-34` gives OOM counts

## 8. Library readiness

### Transfers as it is

- **Leaf aspects whose class keys use only `pkgs`, `lib` and `config`.** Examples are
  `A/hardware/bluetooth.nix` and `A/virtualization/docker.nix`. They do depend on the `persist`
  quirk existing. A library would ship the quirk declaration and a collector, or document that
  the key is inert when neither is present (§4).
- **The settings mirror.** The aspect declares, the host sets, and the aspect reads
  `host.settings.<path>`. Two pieces would have to move into the library or be documented as a
  requirement: `den.reservedKeys = [ "settings" ]` and the `_settings-type.nix` generator
  mounted on the host schema. Without the generator, `host.settings.*` does not exist and every
  reader fails. `docs/host-aspect-settings.md` already says it is written to be replicated.
- **Quirk plus collector**, for example `firewall`, `persist`, `age-secrets`, `nixpkgs-overlays`
  and `homebrew-cask`. The pattern is general. The library has to own both the declaration file
  and the collector, or a consumer's include set silently drops emissions.
- **The platform-routed home classes** (`classes/home-platform.nix`). This file is
  self-contained and copyable.
- **One-way platform arms (`homeLinux` plus `homebrew-cask`).** They cannot break a platform
  that lacks the consumer.

### Quirks and data flow: the yardstick (provisional 9)

The full chain has four steps:

1. **Declare** a quirk as a one-line file with a description (`modules/den/quirks/*.nix`).
   - At this sha there are 48 names in 53 `den.quirks` references under `modules/den`.
   - The extract counts 189 references. The 53 here count only declaration lines.
   - Some descriptions also give the record schema (`quirks/served-domains.nix:2`).
2. **Emit** from an aspect, as a sibling key that is either a value or a function of context.
3. **Route** through a `den.policies.*` pipe attached to an entity schema.
4. **Consume** in a collector or class function that names the quirk as an argument.

What makes this "intelligent use":

- Hosts never list their peers. Peer sets are derived from what each host emits.
- The pipe verbs are chosen by scope: `collect` stays in the environment, `collectAll` spans the
  fleet, `expose` goes up, and `broadcast`/`transform` push to targets chosen by a predicate.
  Each choice is commented (`pipes.nix:70,100,238-243`).
- Producers are not only hosts. Domains, clusters and environments produce too, and some
  consumers are not NixOS at all (terranix for unifi and Cloudflare, nixidy for k8s).
- A setting gates an emission (`openssh.nix:42`) or the routing of a pipe (`nixpkgs-overlays.nix:22`).
- The routing policy sits next to the quirk it serves when the quirk is local
  (`quirks/nixpkgs-overlays.nix`, `xmsg.nix:62,70`, `ninfer.nix:53,69`).
- A quirk with no collector included does nothing, which is how platform-specific emitters stay
  safe (`chromium.nix:48`).

- D7, D8 and D17.
- D4 and D6: the two places where data was hard-coded or copied where a quirk field or a quirk
  was called for.
